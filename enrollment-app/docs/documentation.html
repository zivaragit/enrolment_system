1. System Overview

The Enrollment System is a web application that does two things:

  1. Collects enrollment information from end users through a public, mobile-friendly form.
  2. Consolidates all submissions into an admin dashboard with summary statistics, charts, a searchable/filterable table, and CSV/Excel export.

It is a serverless single-page application: the browser talks directly to Firebase Cloud Firestore, and all access control is enforced by Firestore Security Rules. There is no backend server to deploy or maintain.

Two user roles

RoleAccessCapabilities
Public user No login required Open the enrollment form, submit details, receive a unique reference number (e.g. ENR-2026-00042). Cannot read anyone's data.
Admin Email/password login View dashboard stats & charts, browse/search/filter/sort enrollments, open record detail, change status, export reports.

Key design principle — config-driven form

Every form field (name, label, type, validation, options) is declared in a single file, src/config/formSchema.ts. The public form, the validation schema, the admin table columns, and the export are all derived from it. When the field list changes, you edit that one file — nothing else.

How requests are secured

  • No server-side trust boundary is bypassed — even though the browser writes directly to Firestore, the Security Rules reject anything that doesn't match the allowed shape and role.
  • The public bundle only ships the enrollment form; the admin code (charts, export, table) is lazy-loaded on demand, keeping the public page fast.

5.2 Configuring the form fields

Edit src/config/formSchema.ts. Each field is one object:

{
  name: 'fullName',          // dot-path; "address.city" nests into an object
  label: 'Full Name',
  type: 'text',              // text | email | tel | date | select | textarea
  required: true,
  placeholder: 'Jane Doe',
  pattern: '^[+]?[0-9 ()-]{6,20}$',   // optional regex (text/tel)
  patternMessage: 'Enter a valid phone number.',
  options: [...],            // for 'select'
  section: 'Personal Details',// groups fields under a heading
  showInTable: true          // show as an admin table column
}

The dropdown option lists (PROGRAM_OPTIONS, gender, source) and the STATUS_OPTIONS live in the same file. Adding a program is a one-line change.

Why this matters: the client's exact field list is still being finalised. Because the form is config-driven, applying their answers is a minutes-long edit to one file, not a rewrite.

6. How to Run

Option A — Local with Firebase Emulator (recommended for dev/demo)

No real Firebase project required. Requires the Firebase CLI and Java.

# one-time
npm install
npm install -g firebase-tools        # if not already installed
cp .env.example .env                 # then set VITE_USE_EMULATOR=true

# run (three terminals)
npm run emulators                    # 1) Auth + Firestore + Emulator UI
npm run seed                         # 2) create admin + 40 sample records
npm run dev                          # 3) app at http://localhost:3000

Then open http://localhost:3000/. Sign in to the admin area at /admin/login with the seeded account:

FieldValue
Emailadmin@enroll.test
Passwordadmin123
Port already in use? If port 8080 (or 9099) is taken on your machine, run the emulator on alternate ports and set VITE_FIRESTORE_EMULATOR_PORT / VITE_AUTH_EMULATOR_PORT in .env to match. The app reads the emulator host/ports from those variables.

Option B — Real Firebase project

  1. Create a Firebase project; enable Firestore, Authentication → Email/Password, and Hosting.
  2. Copy the web app config into .env; keep VITE_USE_EMULATOR=false.
  3. Create an admin user in Authentication → Add user.
  4. In Firestore, create a document in collection admins with document ID = that user's UID and fields { email, role: "admin", active: true }.
  5. Deploy rules & indexes, then run the app: 
    firebase deploy --only firestore:rules,firestore:indexes
npm run dev

8. Technical Details

8.1 Config-driven form & dynamic validation

validation.ts walks FORM_FIELDS and builds a Zod object schema at runtime — including nesting dot-path names like address.city into sub-objects. Required string fields get a non-empty check; emails get a regex; optional fields accept empty strings. FormField.tsx renders the correct input (text/select/textarea/date) purely from the field's type.

8.2 Enrollment creation (atomic, race-safe)

createEnrollment() in lib/enrollments.ts runs everything in one runTransaction: all reads (counter, dup markers) happen first, then all writes. This guarantees sequential IDs and duplicate prevention even under concurrent submissions.

ENR-<year>-<seq:5>       // e.g. ENR-2026-00042
serverTimestamp()         // createdAt, stored in UTC
createdDate: "YYYY-MM-DD" // duplicate-free date for range queries
dupKey: "email|phone"     // composite key (audit)

8.3 Duplicate guard without exposing data

Public users cannot read the enrollments collection, so a normal "query before insert" check is impossible. Instead the app uses tiny marker documents in a dupKeys collection (IDs email:… and phone:…). Rules allow existence checks and creation but not listing — so duplicates are blocked without leaking who enrolled.

8.4 Pagination strategy (scales to 10k+ — NFR-5)

SituationStrategy
No search / no date rangeCursor-based server pagination (25/page) via startAfter — cheap, scales indefinitely.
Search or date range activeFetch the equality-filtered set (program/status) and paginate + full-text filter client-side — Firestore has no native text search.

8.5 Dashboard statistics

Summary cards use Firestore getCountFromServer aggregation (counts without downloading documents). Per-program counts are six cheap aggregation queries. The time-series chart groups the most recent records by day.

8.6 Export

lib/export.ts flattens each enrollment (including nested address) into a labelled row and uses SheetJS to produce .xlsx (with column widths) or .csv. The download filename is timestamped.

8.7 Auth & route guarding

AuthContext subscribes to onAuthStateChanged; on sign-in it reads admins/{uid} to decide isAdmin (and honours an active flag). ProtectedRoute redirects non-admins to the login page, preserving the intended destination.

8.8 Performance (NFR-2)

The admin bundle (Recharts + SheetJS) is lazy-loaded with React.lazy, so the public enrollment form downloads only what it needs. Timestamps are stored in UTC and displayed in the visitor's local timezone (NFR-6).

9. Data Model

Collection: enrollments/{autoId}

{
  "enrollmentId": "ENR-2026-00042",   // human-readable, sequential
  "fullName":   "Jane Doe",
  "email":      "jane@example.com",
  "emailLower": "jane@example.com",   // normalised for matching
  "phone":      "+15551234567",
  "dob":        "1995-06-15",
  "gender":     "female",
  "program":    "web-development",
  "source":     "social-media",
  "address":    { "line1": "", "city": "", "state": "", "zip": "" },
  "status":     "new",                // new | verified | rejected
  "createdAt":  <serverTimestamp>,     // UTC
  "createdDate":"2026-06-11",         // for date-range queries
  "dupKey":     "jane@example.com|+15551234567"
}

Collection: meta/counters

{ "enrollmentSeq": 42,
  "year": 2026 }

Incremented +1 inside the enrollment transaction to mint sequential IDs.

Collection: admins/{uid}

{ "email": "admin@client.com",
  "role":  "admin",
  "active": true }

Document ID = Firebase Auth UID. Managed from the console.

Collection: dupKeys/{email:…|phone:…}

No-PII marker docs used to block duplicate email/phone within the enrollment transaction. Existence-checkable and creatable by the public; not listable.

Status lifecycle (FR-2.9)

new (on submission)  →  verified  or  rejected  (set by an admin on the detail page).

10. Security Rules

All access control lives in firestore.rules. Summary of the enforced model (NFR-3):

CollectionPublic (unauthenticated)Admin
enrollmentscreate only, and only if the document has the required keys, a valid email, a non-empty name, status == "new", and createdAt == request.time. Cannot read.read / update / delete
meta/countersread + increment, but only by exactly +1full
dupKeysget (existence) + create; cannot listupdate / delete
adminsread own doc only; writes forbiddenread own doc (writes via console)
function isAdmin() {
  return request.auth != null &&
    exists(/databases/$(database)/documents/admins/$(request.auth.uid));
}

match /enrollments/{id} {
  allow create: if incomingIsValid();      // shape + email + status:"new"
  allow read, update, delete: if isAdmin();
}
match /meta/counters {
  allow update: if request.resource.data.enrollmentSeq
                   == resource.data.enrollmentSeq + 1;   // +1 only
}
Verified: 8 automated rule tests confirm anonymous users cannot read enrollments, cannot write admins, cannot create non-"new" records, and cannot jump the counter by more than one — while admins can read. See §12.

12. Testing & Verification

Three verification suites ship with the project (run against the emulator).

Security-rule & data-path tests — npm run verify:rules

Uses the Firebase SDK to assert the rules behave correctly. Result: 8/8 passing.

  • anonymous CANNOT read enrollments
  • anonymous CAN create a valid enrollment
  • create with missing fullName is rejected
  • create with status ≠ "new" is rejected
  • anonymous CANNOT write to admins
  • counter cannot jump by +2 / +1 increment allowed
  • admin CAN read enrollments

End-to-end UI test — npm run verify:e2e

Drives the real UI in headless Chrome. Result: 7/7 passing.

  • enroll page renders
  • submission succeeds with a sequential reference number
  • duplicate email is blocked
  • admin login → dashboard shows totals
  • enrollments table renders paginated rows
  • search finds the new enrollment
  • no uncaught page errors
The e2e test needs a Chrome/Chromium binary; set CHROME_PATH if it isn't at /usr/bin/google-chrome.

Manual test checklist

Form validation per field · duplicate blocked · ID uniqueness under load · anonymous read denied · admin login (wrong password, logout, session) · pagination >100 records · filters/search correctness · export opens in Excel and matches the view · mobile rendering at 360px · timezone display.

13. Troubleshooting

SymptomCause / Fix
Emulator won't start: "port taken"Another service holds 8080/9099. Change the ports in firebase.json (or a config override) and set the matching VITE_*_EMULATOR_PORT values in .env.
"Could not start Firestore Emulator"Java is not on the PATH. Install a JDK (11+).
Admin login succeeds but dashboard is blockedThe user has no admins/{uid} document. Create one with the user's UID (emulator mode: npm run seed does this).
Dashboard/table emptyNo data yet. Submit via the form, or run npm run seed in emulator mode.
"Missing or insufficient permissions"Rules not deployed, or reading as a non-admin. Deploy rules; confirm the admin doc exists.
Query needs an indexDeploy firestore.indexes.json, or click the console link in the error to auto-create.
Submission blocked unexpectedlyDuplicate guard matched an existing email/phone. Set VITE_BLOCK_DUPLICATES=false to allow repeats.
